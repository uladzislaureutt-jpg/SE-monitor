# data/ml/raw_history — сырой архив классификационных решений

Начиная с update75 (2026-09-03), каждый плановый (не dry-run) запуск
мониторинга архивирует свой полный вывод сюда, в git, прежде чем артефакт
GitHub Actions истечёт (14 дней для `reports/`, 7 дней для `debug/`). До
этого изменения материал каждого дня терял без возможности восстановления,
если его не скачали вручную — единственным источником данных для пилота
SetFit (`ml/setfit_pilot/`, создан 22.08.2026) была именно такая вручную
собранная выборка.

## Что здесь лежит

- `articles/run-<N>_social_articles_<YYYY-MM-DD>.csv` — включённые
  (`KEEP`) кандидаты с полной классификацией: `category`, `subcategory`,
  `signal_type`, `event_object`, `event_problem`, `category_bonus_only` и
  т.д. Точная копия `reports/social_articles_*.csv` того запуска.
- `rejected/run-<N>_rejected_signals_<YYYY-MM-DD>.csv` — отклонённые
  (`REJECT`) кандидаты с причиной отклонения. Точная копия
  `debug/rejected_signals_*.csv` того запуска.

Префикс `run-<N>` — номер запуска GitHub Actions
(`GITHUB_RUN_NUMBER`), не просто дата: несколько запусков (ручные
повторы, dry-run проверки) могут прийтись на один календарный день и
иначе молча перезаписали бы файлы друг друга.

## Для чего это

Это **сырой материал**, не готовый датасет. Он не размечен независимо —
`category`/`event_object`/`signal_type` здесь получены тем же
regex-классификатором, который мы отлаживаем в основном коде, то есть это
условно SILVER-уровень (слабая разметка), не GOLD. Чтобы получить новый
GOLD test для `ml/setfit_large_experiment/` (там текущий статус —
`AWAIT_NEW_BLIND_GOLD`), нужно:

1. Взять случайную (не отобранную по известным багам!) выборку строк
   отсюда за период после создания текущего GOLD (после 22.08.2026);
2. Вручную подтвердить или поправить `KEEP`/`REJECT` для каждой —
   независимо от того, что сказал классификатор;
3. Оформить в том же формате, что `data/ml/event_safe_v1/` (event-safe
   train/validation/test split, без утечки одного события между split).

Разметка — редакторское решение, этот архив только даёт из чего выбирать.

## Dry-run

Во время dry-run (`inputs.dry_run == true`) архивация не выполняется —
это часть контракта "dry-run не меняет состояние репозитория", который
уже проверяется отдельным шагом workflow для `state.json`/
`discovery_cache.json`.

## Рост объёма

При текущем темпе (~15–25 строк/день по будням) годовой прирост — единицы
мегабайт, ретеншн пока не нужен. Если объём станет проблемой — см.
обсуждение в истории апдейтов про `retain_seen_days` для `state.json`,
тот же подход применим и здесь.
